# 系统化排障

## 何时用
任何"它不该这样"的时刻：报错、断言失败、行为与预期不符、修了一处坏了另一处。

## 四条规矩

1. **先复现。** 写出一条能一键复现的命令，记下退出码和关键输出。
   没复现就不要开始改——那叫碰运气。
2. **先定位，再改。** 找到具体文件 + 行号，或者具体的结构路径（哪个字段、哪个键）。
   能说出"为什么会出现这个现象"之前，不许动手。
3. **一次只改一处。** 改完立刻重跑同一条复现命令，把前后输出并排看。
   同时改三处，出错时你分不清是哪一处起的作用。
4. **证明修好了。** 不是"我现在看不到报错了"，而是"原来那条复现命令现在退出 0"，
   再补一条回归断言，防止下次复发。

## 反模式（见到就是走错路了）

- 加 `try/except` 把异常吞掉 → 症状消失，根因还在
- "我猜是缓存问题"然后清了缓存试试 → 猜中了也不知道为什么
- 改了一圈代码，最后说"好像好了" → 没有证据，等于没修
- 扩大范围重构"顺手修一下" → 把可控的 bug 变成不可控的改动

## 交活时要说清

- 复现命令 + 退出码
- 根因（具体到文件行号或结构路径）
- 改了什么（diff 或段落）
- 修复后的同一条命令输出
