# 测试先行

## 三步，顺序不能换

1. **先让测试红。** 写断言，对着**现在的代码**跑，必须失败。
   贴出失败输出——这是"测试真的在测东西"的唯一证据。
2. **再让它绿。** 改实现，跑到通过。贴通过输出。
3. **再证明它抓得住旧问题。** 把代码退回旧版本跑同一条测试，必须变红（RED 验证）。

> 第 3 步最容易被跳过，也是最有价值的一步。
> "新测试通过"可能只是测试写松了；"新测试能让旧版本变红"才证明它有效。

## 断言写在哪一层

| 想验证的 | 该写在哪 |
|---|---|
| 函数行为 | 单元测试，输入输出 |
| 文件/数据被改了 | 读回产物断言结构字段，别只搜字符串 |
| 源数据没被改 | 前后全量哈希对比（**副作用也要测**） |
| 错误路径 | 故意触发，断言可读报错 + 进程没崩 |

## 反模式

- 先写实现再补测试 → 测试只会迁就实现，抓不到问题
- 断言"文件存在"就算通过 → 存在不等于内容对
- 只测 happy path → 错误路径才是事故高发区
- 为了让测试过而改测试 → 那不是修 bug，是掩盖 bug
